# ex603-game-telemetry-database

**Theme:** Game Telemetry

This project showcases a game telemetry database that collects, analyzes, and utilizes data of a multiplayer video game.

## Domain

For the project, there are six domains that it could take the form of, all sharing the underlying structure of five rows: actor, producer, event, catalog, and junction, alongside a numeric metric.  The domain that I chose for mine is Game Telemetry, where the player serves as an actor, the match serves as the producer, match participants serves as an event, game modes serve as a catalog, match modes serve as the junction, and score serves as the metric.  The reason I chose this domain is because I have a passion for video games, as I have played a wide variety of their genres, including (but not limited to) adventure, FPSes, puzzles, racing, and strategy games.

Although I am more into single-player games, I have also played (competitive) multiplayer games, such as Call of Duty.  In the case of my project, I will emulate a game telemetry database of a competitive online multiplayer FPS game, since I have always believed that no games of that kind is complete without it.  By creating the project, I am looking forward to answer how the data is collected and managed by that game, given that I should be familiar with data management subjects since my years as an undergraduate.

## Database overview

![](schema/ERD.png)

* **Players** - An actor table that stores player records.  Here, each player is identified with a unique username to prevent confusion, along with their unique ID serving both as a primary key of this table and surrogate key for performance-related purposes.
* **Matches** - A producer table that stores game match records.  Here, each match is mainly identified by its unique ID, also a surrogate key for performance-related purposes, and they have a status attribute that indicates whether it is active, is inactive, or has ended.  It also has another attribute that tracks how many players are participating in it, which could be used in queries with sorting or filtering purposes.
* **MatchParticipants** - An events table that serve as a connection between matches and players.  In it, a player can participate in many matches, but they can only participate in the same match at least once.  For each player participation, a timestamp that records when the player joined the match is included, along with their score.  In addition, each player participation comes with an attribute that indicates the player's status (i.e. Victory, Draw, or Defeat), faction (if the match is set to a team-based gamemode), and a few other statistics (i.e. kills, deaths, and assists) in the match.  This table uses a composite primary keys of player and match IDs that serve as foreign keys to their respective tables.
* **GameModes** - A catalog table that stores game mode records.  Here, each game mode is identified with a unique name to prevent confusion, along with its unique ID serving both as a primary key of this table and surrogate key for performance-related purposes.  In addition, each game mode comes with its description, as well as a boolean that identifies whether the mode is team-based or not.
* **MatchModes** - A junction table that serves as a connection between matches and game modes.  Here, a game mode can be associated with many matches, but a match should only be assigned exactly one game mode.  This table uses a composite primary keys of match and game mode IDs that serve as foreign keys to their respective tables, alongside a timestamp attribute that records when the match is assigned its game mode.

## Technical highlights

Here are the three of my techniques that I have applied in my queries.

1. **JOIN (left table) ON (right table).(right key) = (left table).(left key)**

I use the JOIN clause, which naturally functions as an INNER JOIN (unless I add either LEFT, RIGHT, or (FULL) OUTER right before the word JOIN), to join the table that identifies an entity by its ID with another table that also identifies it by its name, such that I would identify it as the latter in the resulting table while writing down the query.  For example, while searching for players that has participated in a match, I would want to find their actual usernames, and either alongside or not their IDs.

2. **CTEs**

CTEs modularizes the querys that I write, as I am able to verify test parts of them without changing much, compared to using subqueries.  I primarily use them to break down complex tasks into managable parts, ranging from exclusively finding matches that lack any participation records to filtering the ranked players to the top three per match.

3. **Window functions**

Window functions (i.e. OVER clause) allow me to simultaneously compute the (per group) aggregation(s) and preserving the individual rows, such that I perceive the aggregation in more detail than how I did when I use GROUP BY alone.  Not only that, I would also use this to assign rankings to entities based on the attribute(s) and condition(s) that I specify.  Examples of using window functions includes, but are not limited to, calculating the running total and moving average scores to see how they accumulated and changed overtime, respectively, along with ranking players by score per match.

## Findings and recommendations

One thing that I found is that there are a few matches that are not associated with any participation records.  At this rate, they do not have any associated players, despite what their stated player count attributes say in the Matches table.  Besides, the matches' stated player count may not accurately equal the actual number of players as its participants, let alone indicating whether the match is active or not, if it is not defined or set up properly.  In conclusion, not only I would have the player count attribute function as a derived attribute that accurately syncs with the aforementioned actual amount based on its participants, but I would also include a flag that explicitly states the matches' statuses, be it either inactive, active, or completed.

Another thing I found is that the scores earned by match participants overtime is not on a consistent, upward or downward trajectory, but rather as inconsistent and undulate as driving throughout rolling hills.  This means that the description that I have described in the previous sentence can be applied the rate of players' participations ending disgracefully (for reasons such as the players quitting themselves or, most importantly, network timeouts), besides the rate of players playing the game. As such, I can say that the game’s stability, in terms of networks (mainly this one) and players’ hardware, is inconsistent and needs to be addressed via fixes, including, but not limited to, addressing bugs and improving the back-end.  This can be done alongside maintaining the game’s fun factor and re-balancing difficulty that ensures the more consistent and positive rate of players playing the game every month.
