# Modeling Justification

First, in the actor schema named Players, I chose this key, named pID, as the primary key.  It would serve as a unique, stable identifier (in the form of an integer) to each player in this schema, particularly in case a player wants to change their display name, which is stored as the Username attribute in this schema.  While defining Username as the primary key is a poor choice for obvious reasons, I included the constraints NOT NULL and UNIQUE for it, since multiplayer video games typically display their usernames when identifying them instead of their harder-to-remember ID, alongside the fact that no two players can share the same name.

Secondly, about the producer schema, Matches, I selected the key mID as the primary key.  The reason is similar to the one I described in the first half of the first paragraph above, as it serves as a unique ID for a game match in a more stable manner than using its name, stored as the MatchName attribute in this schema.  Speaking of the latter, I did not define any constraints for it, as video games typically do not specifically name the matches, at least from my experience as a player.

Next, for the event schema called MatchParticipants, I defined two foreign keys, with the first one identifying the player by their ID from Players and another identifying the match, that they participate in, by its ID from Matches.  For each row that records the player’s participation in a match, the timestamp and player’s scores would be both recorded and stored as the mpTimestamp and Score attributes, respectively, alongside additional information.  I defined Score with the constraints NOT NULL and CHECK, as it must both be a positive integer (or not less than 0) and not be left blank.  Also, I set the first foreign key that identifies the player to have the ON DELETE CASCADE constraint and the second one that identifies their match to have the ON DELETE SET NULL constraint, such that upon deletion of a player from Players removes the row that records their participation regarding the match and deleting the match from Matches preserves that row with the second foreign key set to NULL.  I specified these ON DELETE behaviors given that I assigned the first foreign key with the NOT NULL constraint, as I have always known that no participation is complete without a person.

Speaking of the catalog named GameModes, I considered the key gmID a unique, stable ID for a game mode for a reason that is similar to that of choosing pID and mID as primary keys for Players and Matches, respectively.  Unlike Matches, each gamemode is given a unique name, which is true for many multiplayer games that I played, which is why I set the ModeName attribute that stores it to have the NOT NULL and UNIQUE constraints.

Finally, for the junction schema called MatchModes, I designed a composite primary key over two foreign keys, with the first one referring to the match by its ID in the Matches schema and the second one referring to the gamemode by its ID in the GameMode schema as requested by the Project Setup and Overview section of Unit 1.  In addition, I set both of the foreign keys of this schema to have the ON DELETE CASCADE constraint, such that removing a match from Matches deletes its record from MatchModes, while removing a gamemode from GameMode deletes its record of its associated matches from MatchModes as well.

# Reflection

Multiplayer games comes in not just one genre, but rather many genres that range from first person shooters (FPS) to real-time strategy (RTS) and card games.  In terms of game telemetry databases, although multiplayer games may share some of the attributes together, they require and track other attributes that are different and/or unique, depending on the genre fulfilled.  For me, I chose my project to emulate the database of a multiplayer FPS game, akin to Call of Duty, that I should be more familiar with.  That way, I introduced additional attributes to the schemas that I think would be unique to a game of that kind, including kills and deaths, alongside familiar ones shared across multiplayer games like player levels and match outcomes.

I must admit that I intend the cardinality of MatchModes to be one-to-many rather than many-to-many, as shown on my ERD diagram.  This is because I think that each match should have exactly one gamemode, such as deathmatch and capture-the-flag, but it can be associated with many matches.

There exists an aspect that I am confused about, however.  I had to include a numeric attribute that I could use for filtering matches in the Matches schema, and I did.  The problem was that I could not figure out what that attribute is supposed to be in the context of a multiplayer FPS.  It could be anything that I could think of, but again, I am not fully sure about the numeric attribute for the matches, for now.
