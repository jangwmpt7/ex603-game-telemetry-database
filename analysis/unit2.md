# The constraints table

| Foreign Key | ON DELETE Choice | Explanation |
| --- | --- | --- |
| MatchParticipants.pID | ON DELETE CASCADE | When a player is deleted from the Players table, their corresponding information of the matches they participate in gets deleted as well. |
| MatchParticipants.mID | ON DELETE RESTRICT | For the match to be removed from the Matches table, all information about its participants must be removed from MatchParticipants first. |
| MatchModes.mID | ON DELETE CASCADE | When the match gets deleted from the Matches mode, its information about its chosen gamemode gets deleted as well. |
| MatchModes.gmID | ON DELETE RESTRICT | For the gamemode to be removed from the GameModes table, all its associated matches must be deleted from MatchModes first. |

For MatchParticipants.pID, ON DELETE CASCADE ensures that the player’s information of all the matches they participate in (in the form of rows given their pID) gets removed once that player is removed from the Players table.  This does not affect such matches (as long as they have concluded at the time), as they would remain in the Matches table alongside other players’ info about their participation in these matches in the MatchParticipants.  Had it not been for this ON DELETE choice, then the pID of the affected rows in MatchParticipants when the player is removed from Players by their pID would cause errors given that it both has a NOT NULL constraint and is one part of a composite primary key of the former, with mID being the other part.

For MatchParticipants.mID, ON DELETE RESTRICT prevents removing the particular match (given its mID) from the Matches table, unless the players’ participation data of this match are removed from MatchParticipants first.  Initially, I considered implementing ON DELETE SET NULL for mID in MatchParticipants instead back when that and pID were not designed as primary keys, as doing that same task would set the mID values in affected rows to NULL, but it could make the data on the table look confusing, especially when multiple matches that share at least one player as their participant gets removed.  This is why I decided to change the ON DELETE behavior to RESTRICT forMatchParticipants.mID.

For MatchModes.mID, ON DELETE CASCADE ensures that the match’s information about its gamemode (given its mID) is removed upon removing the match from the Matches table.  This will not affect the affected gamemode that the match was, as the GameMode table remains unaffected.  It is a similar situation with the one described at the end of the first paragraph had it not been for ON DELETE CASCADE, as mID also has a NOT NULL constraint alongside being one part of a composite primary key of MatchModes, with gmID being the other part.

For MatchModes.gmID, ON DELETE RESTRICT prevents removing the particular gamemode from the GameModes table, unless the matches that chose this gamemode are removed from MatchModes first.  I changed this behavior from ON DELETE CASCADE, which would remove the matches’ records of the chosen gamemode that was affected, but this would also remove an indication whether the match was team-based or not (as I later added that as an attribute to the GameModes table after changing the ON DELETE behavior), therefore adding at least a sense of confusion. 

# The CHECK constraints

There are currently five CHECK constraints in the database.  The first one is chk_player_no_self_referral, which prevents an individual player from referring to themselves by their own pID in the referred_by attribute.  That would be an invalid state for that attribute, which would arise in the event that I mistakenly add a record of the player whose referred_by attribute is of the same value as their pID.  Second, chk_player_XP_Level ensures that the player’s XP and Level never goes below 0 and 1, respectively.  The invalid states for these two attributes would be any negative number, plus 0 for the Level attribute, and they would arise should I implement a feature where a player loses XP from losing matches repeatedly, which results in lowering their level when their XP is low enough.  The next CHECK constraint, chk_status, enforces the three possible values for the Status attribute to either have in Matches, including ‘starting’, ‘running’, and ‘over’.  Its invalid states include any other string, including typos of these words (i.e. ‘ovrt’) that could be accidentally entered while inserting or updating the match’s record.  Then, chk_faction enforces the three possible values for the Faction attribute to either have in MatchParticipants, including null, ‘alpha’, and ‘beta’.  Finally, chk_outcome enforces the four possible values for the Outcome attribute to either have in the said table.  About the latter two attributes’ invalid states and how they would arise, it is a similar story with the Status attribute.

# What has changed in Unit 2

Over the course of the second unit, I have updated my schema by changing the ON DELETE behaviors of MatchParticipants.mID and MatchModes.gmID from SET NULL and CASCADE, respectively, to RESTRICT for both, as I have described earlier.  Not only that, I added in new attributes (and their constraints) as well.  They include the email, joined_at, and referred_by for Players (with the latter being a foreign key that refers to pID in the same table, alongside having the aforementioned chk_player_no_self_referral); the Description and TeamBased attributes (that details what a gamemode is and indicates whether it is team-based or not, respectively) for GameModes; the assigned_at attribute (that records the timestamp of when the match is assigned a gamemode) for MatchModes; and the Faction attribute (that records the player’s faction during the match as either ‘alpha’ or ‘beta’, as long as the match’s gamemode is team-based) for MatchParticipants.  Plus, I have figured out that the numeric attribute for the Matches table would track how many players participated in a match.  That would function best as as a derived attribute, however, so it will not be defined inside the Matches table’s definition in schema.sql, with a comment that describes that attribute taking its place.

With these updates in mind, I updated my files in the schema folder, including the ERD, accordingly.
